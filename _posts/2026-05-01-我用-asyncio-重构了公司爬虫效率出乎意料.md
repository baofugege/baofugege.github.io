事情是这样的：上周运维告警，我们那个老爬虫把数据库连接池打满了。一查代码，用 `requests` + `for` 循环逐个抓 200 个 URL，每个请求阻塞 2 秒，一轮跑下来要六分钟。老板问我能不能优化，我说可以，换 asyncio。结果改完跑一轮只要 35 秒，领导还以为我删了什么数据。这篇文章就把真实改造过程记录下来，包含完整可跑的代码和你一定会踩的坑。

## 为什么是 asyncio，而不是多线程？

很多人一提并发就开 `ThreadPoolExecutor`，但对于爬虫这种 IO 密集型任务，线程切换的开销和 GIL 的掣肘会让收益打折。asyncio 用**单线程 + 事件循环**的方式，当一个协程在等网络响应时，事件循环立刻切到另一个就绪协程，CPU 不再空转。

它的核心概念就三个：

- **协程 (coroutine)**：`async def` 定义，用 `await` 挂起当前任务交出控制权。
- **事件循环 (event loop)**：调度所有协程，谁就绪就跑谁。
- **Future / Task**：代表一个“未来会完成”的结果，`asyncio.gather()` 可以并发等待多个。

我第一次真正理解它，是写了一个对比 demo：用同步和异步分别请求 20 个 URL，同步 40 秒，异步 2 秒。下面就是这个 demo 的核心代码。

## 先看一个最小可行对比

```python
import asyncio
import time
import httpx  # 支持 async 的 HTTP 客户端

URLS = [f"https://httpbin.org/delay/1?t={i}" for i in range(20)]

# ---------- 同步版本 ----------
def fetch_sync(url: str) -> str:
    with httpx.Client() as client:
        return client.get(url).text

def run_sync():
    start = time.perf_counter()
    results = [fetch_sync(url) for url in URLS]
    elapsed = time.perf_counter() - start
    print(f"同步耗时: {elapsed:.1f}s")  # 约 20s+

# ---------- 异步版本 ----------
async def fetch_async(client: httpx.AsyncClient, url: str) -> str:
    resp = await client.get(url)
    return resp.text

async def run_async():
    start = time.perf_counter()
    async with httpx.AsyncClient() as client:
        tasks = [fetch_async(client, url) for url in URLS]
        results = await asyncio.gather(*tasks)
    elapsed = time.perf_counter() - start
    print(f"异步耗时: {elapsed:.1f}s")  # 约 2s

# 入口
if __name__ == "__main__":
    run_sync()
    asyncio.run(run_async())
```

这里 `asyncio.gather()` 一次性把所有协程提交给事件循环，并发等待，总耗时约等于最慢那个请求的时间（加上一点调度开销），而不是线性累加。`httpx.AsyncClient` 在底层复用了连接池，也不用每次都挥手握手。

## 实战改造：200 个 URL 的爬虫

我们真实的爬虫需要从 200 个分页接口抓 JSON，然后解析存入数据库。同步版本核心就是 `for page in range(1, 201): requests.get(...)`。现在改成异步，还要控制并发——如果 200 个请求同时打出去，目标服务器可能直接把你 IP 封禁。

我用 `asyncio.Semaphore` 做并发控制，同时最多 20 个协程在跑：

```python
import asyncio
import httpx
from typing import Any

BASE_URL = "https://api.example.com/data?page={}"
CONCURRENCY = 20  # 并发上限
PAGES = range(1, 201)

async def fetch_page(
    client: httpx.AsyncClient,
    sem: asyncio.Semaphore,
    page: int
) -> dict[str, Any]:
    """抓取单页，受信号量控制并发数"""
    async with sem:
        url = BASE_URL.format(page)
        resp = await client.get(url)
        resp.raise_for_status()  # 非 200 直接抛异常
        return resp.json()

async def main():
    sem = asyncio.Semaphore(CONCURRENCY)
    # 连接池配置：总连接数 = 并发数，避免资源浪费
    limits = httpx.Limits(max_connections=CONCURRENCY,
                          max_keepalive_connections=CONCURRENCY)
    async with httpx.AsyncClient(limits=limits, timeout=30.0) as client:
        tasks = [fetch_page(client, sem, page) for page in PAGES]
        results = await asyncio.gather(*tasks, return_exceptions=True)

    # 处理结果：分离正常数据和异常
    success = []
    errors = []
    for page, res in zip(PAGES, results):
        if isinstance(res, Exception):
            errors.append((page, res))
        else:
            success.append(res)

    print(f"成功 {len(success)} 页, 失败 {len(errors)} 页")
    # 后续入库逻辑...
    return success

if __name__ == "__main__":
    asyncio.run(main())
```

注意 `return_exceptions=True`：这样哪怕某个页请求超时也不会中断其他任务，异常会被包裹成 `Exception` 对象返回到列表中，我们可以后续统一处理重试。

## 踩坑实录，每个都真实存在

**坑1：在协程里偷偷用了同步库**  
如果你在 `async def` 里写了 `requests.get()` 或者 `time.sleep()`，整个事件循环就卡死了。尤其是项目里引入的第三方库，比如某些数据库驱动、Redis 客户端，它们默认是同步的。解决方案：要么用异步版本（如 `aiomysql`、`redis.asyncio`），要么用 `asyncio.to_thread()` 把同步调用丢到线程池。

**坑2：`await` 放错位置导致串行**  
新手常写成 `for url in urls: await fetch(url)`，这样还是一个一个来。正确姿势是创建 task 列表然后 `await asyncio.gather(*tasks)`，或者用 `asyncio.create_task()` + 单独 await。

**坑3：Windows 上 `asyncio.run()` 报错**  
Windows 的默认事件循环策略在子进程/多线程场景会报 `RuntimeError`。如果你在脚本里用了 `multiprocessing`，记得在入口加上：
```python
import asyncio
if __name__ == "__main__":
    asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())
    asyncio.run(main())
```

**坑4：`Semaphore` 配合 `gather` 的取消问题**  
如果你的任务被 `gather` 外部取消了，`Semaphore` 的 `async with` 可能不会正常释放，导致信号量泄漏。在需要强健壮性的场景，可以考虑用 `asyncio.wait(..., timeout=...)` 替代 `gather`，并做 `finally` 清理。

## 总结

asyncio 不是银弹，但如果你在写大量网络 IO 的程序却还在串行阻塞，它可能就是那 10 倍提升的关键。
